# 可追溯发布审计

## 审计立场

1. 保持独立和只读；先报告证据，再提出修复建议。
2. 从原始要求重建核查基线，不采信修改者的自我声明作为唯一证据。
3. 对每个事项建立“来源—决策—操作—回应—位置—产物”的闭环。
4. 允许正式拒绝、部分采纳和无需修改；要求理由充分并与最终文件一致。
5. 区分结构性验证、文本证据和专业判断。脚本通过不能代替语义审阅。
6. 将审计报告和测试产物置于正式交付目录之外。
7. 不扩大审计授权；用户要求核查时不得擅自修改正式文件。

始终读取 [references/SPEC.md](references/SPEC.md)。存在台账时读取 [references/TRACEABILITY_CONTRACT.md](references/TRACEABILITY_CONTRACT.md)。学术提交任务再读取 [references/ACADEMIC_PROFILE.md](references/ACADEMIC_PROFILE.md)。

## 工作流

### 1. 冻结审计对象

- 记录目标文件、来源文件、版本、时间和可用哈希。
- 明确正式交付目录与审计报告目录。
- 获取要求清单、反馈原文、决策记录、正式回应和最终产物。
- 缺少台账时，从现有材料重建最小台账，不要求其他 Skill 先运行。

### 2. 建立审计矩阵

为每个事项记录：

- 原始要求及来源；
- 核心问题；
- 最终决策及授权人；
- 声称完成的操作；
- 最终文件中的实际证据；
- 正式回应及其修改位置；
- 关联事项和受影响文件；
- 当前状态与缺口。

可从 [assets/traceability-ledger.template.json](assets/traceability-ledger.template.json) 建立台账，并运行：

```powershell
python scripts/validate_traceability.py <台账.json> --delivery-root <交付目录> --json-out <审计报告.json>
```

### 3. 核验六个层面

1. **保真性**：来源原文、顺序、编号和限定条件是否完整。
2. **响应性**：正式回应是否正面处理核心问题，明确接受程度、行动或理由。
3. **落实性**：回应声称完成的修改是否能在最终产物中找到。
4. **一致性**：相关正文、附件、图表、派生版本和报告是否采用同一口径。
5. **边界性**：正式文件是否含内部过程、过度防御、占位符或未授权内容。
6. **发布性**：文件可打开、版本正确、目录纯净、位置和编号有效。

### 4. 运行确定性检查

- 使用 `scripts/validate_traceability.py` 检查台账完整性与证据路径。
- 使用 `scripts/compare_docx_text.py` 比较 Clean 与标记版的可见文字、引文字段和高亮状态。
- 根据文件类型调用合适的文档、表格、演示文稿或参考文献工具进行结构检查。
- 对脚本无法判断的响应充分性、段落逻辑和专业准确性执行人工或语义审阅。

### 5. 形成结论

- 按 `critical`、`major`、`minor`、`observation` 分级。
- 为每项发现提供规则、文件、位置、证据和修复条件。
- 将“未发现问题”限定于已检查的范围，不作无依据的绝对保证。
- 仅在所有发布门禁通过后给出 `pass`。
- 修复后重新审计受影响项目及其传导范围。

## 独立运行与协议互通

- 无台账时从原始反馈、回应和最终文件重建。
- 无正式回应时审计要求与产物之间的直接落实关系。
- 读取协议主版本为 `1` 的记录；忽略未知字段并保留原数据。
- 不依赖修改协调、边界守卫或写作 Skill。
- 其他 Skill 的报告只能作为线索，必须回到原始来源和最终产物复核。

## 发布门禁

仅在以下条件全部满足时判定通过：

- 每个必须处理的事项均有明确状态；
- 每项正式回应均处理核心问题；
- 所有修改声明均有可核查证据，或明确说明无需修改及理由；
- 关键修改在所有受影响产物中保持一致；
- 正式文件无未解决的禁入内容；
- 派生版本在预期差异之外保持一致；
- 最终目录、编号、引用、位置和文件可用性通过检查；
- `critical` 与 `major` 发现为零。

使用 [references/EVALUATION_CASES.md](references/EVALUATION_CASES.md) 进行前向测试。
