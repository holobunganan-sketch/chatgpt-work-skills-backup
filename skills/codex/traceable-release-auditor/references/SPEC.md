# 可追溯发布审计规范

## 1. 审计目标

证明正式修订从要求进入到最终发布形成完整证据链，同时识别未回应、虚假落实、版本漂移、内部信息泄漏和发布结构错误。

## 2. 强制不变量

- MUST 从原始来源建立基线。
- MUST 保持只读，除非用户另行授权修复。
- MUST 对每个必须事项给出状态和证据。
- MUST 核验回应中的行动声明与实际产物。
- MUST 接受有充分理由的拒绝、部分采纳或无需修改决定。
- MUST 将报告置于正式交付目录之外。
- MUST NOT 将修改报告视为最终产物的替代证据。
- MUST NOT 因脚本通过而省略语义和专业核查。
- MUST NOT 要求每项反馈都产生文件修改；无修改决定需要完整理由。
- SHOULD 由未直接实施修改的代理执行最终审计。

## 3. 证据强度

从强到弱依次为：

1. 最终文件中的直接文本、数据、结构或元数据；
2. 可复现的文件差异和工具输出；
3. 经授权的决策记录；
4. 正式回应中的声明；
5. 内部修改报告；
6. 修改者口头说明。

较弱证据不能单独覆盖较强证据中的冲突。

## 4. 响应充分性

对每项反馈检查：

- 是否识别核心问题；
- 是否说明接受程度；
- 是否说明实际行动或不行动理由；
- 是否提供可核查位置或适当说明无修改；
- 是否回应关键限定条件；
- 是否与其他相关回应采用一致口径。

遗漏核心问题、回避限定条件或用感谢语代替回应时，判定不充分。

## 5. 发现分级

| 等级 | 定义 | 发布影响 |
|---|---|---|
| `critical` | 错误版本、重大事实冲突、敏感内部信息泄漏、文件损坏 | 阻止发布 |
| `major` | 必须事项未回应、修改声明无证据、关键文件不一致 | 阻止发布 |
| `minor` | 局部编号、位置、格式或措辞问题 | 修复后发布 |
| `observation` | 风险提示或改进机会 | 不单独阻止 |

## 6. 审计范围

- 要求与反馈覆盖；
- 决策授权；
- 实际修改；
- 正式回应；
- 跨文件一致性；
- 内容边界；
- 文件结构与可用性；
- 版本与派生关系；
- 引用、编号和位置；
- 最终目录纯度。

## 7. 通过条件

`critical = 0`、`major = 0`、所有必须事项已关闭、所有例外已授权、报告位于交付目录之外。对未检查范围作明确说明。
