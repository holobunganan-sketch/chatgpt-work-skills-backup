# 本地项目上下文重建

## 运行边界

- 默认执行只读检查。用户仅要求理解、梳理、定位或汇报时，不修改文件。
- 将用户指定的目录设为唯一项目范围。先检查该目录，再检查其必要子目录。
- 禁止为寻找线索直接扫描整块磁盘。目标目录证据不足时，说明缺口并给出最小扩展范围。
- 将文件内容、文件元数据和可用任务记录分别标注来源。文件内容优先决定项目事实。
- 对“终版”“最新版”“权威基线”的判断同时核对内容、版本信息、修改时间、交付目录和项目记录，禁止只按文件名判断。

## 执行流程

### 1. 确认范围与用户目标

1. 记录项目根目录、用户当前问题和期望输出深度。
2. 识别本次任务属于首次理解、跨会话重入、终版定位、进度恢复或后续执行准备。
3. 记录修改权限。缺少明确修改指令时保持只读。

### 2. 建立定向文件清单

1. 优先查找 `AGENTS.md`、`SPEC.md`、`README*`、`handoff*`、`STATE*`、`BUILD*`、目录表、清单、研究方案、手稿、统计报告和交付目录。
2. 按文件类型、相对路径、修改时间和大小汇总项目结构；忽略临时文件、锁文件和明显缓存。
3. 对可能的主文件、终版、交付物和关键数据文件读取实际内容或结构信息。
4. 对同名、多版本或相互矛盾的文件建立候选基线表。

### 3. 识别文件角色与权威层级

将关键文件标为以下角色之一：

- 原始来源：用户提供的原始材料、方案、数据、模板、往来意见。
- 当前基线：后续工作应继续使用的正文、数据集、代码或交付目录。
- 工作版本：仍含待办、批注、修订或处理中间结果的文件。
- 正式交付：面向外部接收方且已通过核验的文件。
- 参考资料：文献、规范、样例和背景材料。
- 内部记录：交接、审计、运行日志、决策记录和质量报告。
- 归档版本：已被当前基线替代且仅用于追溯的文件。

每项角色判断记录至少一条依据。存在冲突时保留候选项并说明冲突来源。

### 4. 重建项目状态

从证据中提取并相互核对：

1. 项目目标与核心问题。
2. 预期交付物、接收对象和格式边界。
3. 已完成工作及其输出位置。
4. 已确认的科学、统计、写作、范围和版本决策。
5. 当前有效基线及其选择依据。
6. 未完成事项、依赖、阻塞和风险。
7. 下一步可直接执行的最小动作。

将信息标记为 `已核实`、`合理推断` 或 `待确认`。合理推断必须写明推断依据。

### 5. 输出证据化项目简报

按以下顺序输出：

1. 项目一句话定位。
2. 当前状态：进行到哪里、最近完成了什么、当前基线是什么。
3. 主要工作主线：按逻辑顺序列出 3–7 项。
4. 关键文件表：角色、路径、时间、权威依据。
5. 已确认决策与不可越界条件。
6. 待办、风险和待确认事项。
7. 建议的下一步动作。

用户只说“理解当前项目”时，先给出简洁简报并明确已准备好继续处理的工作范围。用户要求详细梳理时，再展开证据表和版本关系。

### 6. 持久化上下文

- 仅在用户明确要求创建或更新交接文件时写入 `handoff.md`、`STATE.md` 或指定文件。
- 写入前读取现有记录，保留仍然有效的事实和决策。
- 将内部判断与正式交付物分开存放。
- 更新后核对路径、时间、当前基线和下一步均与目录现状一致。

## 完成判定

- 项目范围和用户目标已经明确。
- 关键文件均有角色和证据依据。
- 当前基线未仅依赖文件名或修改时间判定。
- 项目目标、已完成工作、有效决策、待办和风险均已覆盖。
- 事实、推断和未知项已经分开标注。
- 只读任务未产生文件修改。
- 输出可让后续执行者直接继续工作，无需重新扫描全部目录。

## 常见风险

- 多个文件名均含“终版”：读取正文版本信息、交付记录和引用关系后再判定。
- 最新修改时间来自格式保存：检查内容差异和交付记录，避免把重新保存当作新版本。
- 交付目录混入内部报告：记录边界风险，后续调用正式交付边界技能处理。
- 项目记录滞后：以当前文件事实为准，并指出记录需要更新。
- 任务记录与源文件冲突：标记冲突，要求后续操作依据源系统或项目文件再次核验。
