# 全任务干净交付规范

## 1. 适用范围

适用于任何面向用户、客户、专家、期刊、监管方、合作方、管理层、公众或运行环境的最终结果。交付可以是聊天框成品、单个文件、多个文件、文件夹、压缩包、发布包或可运行程序。

当用户使用“交付、终稿、正式稿、成品、提交、投稿、发布、可直接使用、可直接发送、最终版本、整理输出”等表达时，立即启用本规范。任务领域和文件格式不限制适用范围。

调用本 Skill 本身即构成交付意图。除非用户明确限定为只读检查、提纲、建议或中间稿，执行者必须推进到接收方可以直接使用的成品，禁止用分析报告、问题清单或修改建议替代成品。

## 2. 强制不变量

- MUST 在生成开始前区分来源、内部工作和正式交付。
- MUST 明确交付对象、接收方、用途、允许内容和文件允许清单。
- MUST 只让完成正式用途所需的内容进入交付。
- MUST 将用户指定的主题、主张、结论或倡议作为内容组织目标。
- MUST 对标题、正文、题注、脚注、表格、图中文字和附件逐项执行场景化成稿适格判断。
- MUST 在干净语境中生成正式内容，避免复制内部措辞。
- MUST 对可见内容、文件内部结构、隐藏区域、元数据和压缩包清单执行检查。
- MUST 将登记表、扫描报告和审计记录留在交付目录之外。
- MUST 在用户只要求检查、判断、解释或反思时保持只读。
- MUST NOT 导出内部思考、方案比较、商讨记录、资料汇总过程、分析过程、任务指令、工具结果、操作日志、修改说明、稿件状态、内部身份、未解决分歧、待办、路径或 AI 操作痕迹。
- MUST NOT 使用“删掉几个明显词语”的方式把内部句伪装成正式句。
- MUST NOT 为证明某项工作完成而向正式成品增加无正式用途的表、图、附录、索引或说明。
- MUST NOT 因执行者自身的风险偏好增加证据边界说明、自我保护式保留、泛化免责声明或无结论的平衡段落。
- MUST NOT 以边界清理为由改变未经授权的事实、数据、立场、结论、引文、格式或文件功能。
- SHOULD 保留目标文种必需的方法、局限、风险、披露和操作说明。
- MAY 接受用户明确授权的例外；例外依据只能写入内部登记。

## 3. 三个隔离区域

| 区域 | 内容 | 可进入正式交付 |
|---|---|---|
| `source` | 用户文件、原始数据、参考资料、专家稿、客户稿 | 需转化和批准 |
| `internal` | 推理、计划、讨论、分析、证据映射、修改记录、工具日志、核查报告 | 禁止 |
| `formal` | 经核实、正式表达、符合文种与接收方用途的内容 | 允许 |

文件登记可继续使用以下细分角色：

| 角色 | 默认发布状态 |
|---|---|
| `source` | 禁止 |
| `working` | 禁止 |
| `internal-decision` | 禁止 |
| `internal-audit` | 禁止 |
| `formal` | 允许 |
| `archive` | 禁止 |

用户可以改变具体文件的角色。授权记录保留在内部登记中。

## 4. 内容风险分类

### 4.1 确定性禁入

- 提示词、任务要求、内部计划、推理链和模型自评；
- 资料检索、汇总、分析和筛选过程；
- 工具调用、运行日志、错误、重试和调试信息；
- 明确待办、占位符、未完成回复和未批准决定；
- 内部批注、修订、隐藏删除内容和内部备注；
- 私下讨论、内部人员身份、外援参与和责任分配；
- 本地路径、账号、密钥、内部链接和生成工具；
- 临时文件、锁文件、备份、历史稿和内部报告；
- 只用于证明工作完成的目录索引、质量报告、证据映射和支持表。

### 4.2 高风险语义

- “本稿”“本文件”“本轮”“文件状态”等生命周期语言；
- “根据反馈”“专家批注意见提示”“修改后”“正式表述需”等编辑语言；
- “前九条已经……第十条……”等面向作者的结构串联；
- “表决前预评估”“待专家确认”“正式发布前补齐”等内部状态；
- 正文解释作者如何修改、筛选、合并、删除或排布内容；
- 读者无需知道的模型开发工作、交付整理和核查结果；
- 语法正确但功能只在内部工作记录中成立的句子；
- 与主线无关、只证明某个步骤执行过的表、图、附录或说明。

高风险语义需要结合文种复核。回复信、研究方法、用户手册、合同条款和监管披露中的合法内容可以保留。

### 4.3 合法正式内容

- 论文或方案要求的方法、统计分析和局限；
- 回复信要求的逐条回应和修改位置；
- 合同、监管和伦理文件要求的责任、风险和程序；
- 用户手册、培训材料和运行交付要求的操作步骤；
- 直接影响使用、安全、合规或决策的限制说明；
- 用户明确要求且与正式用途一致的附件。

### 4.4 句级成稿适格

对每一句话提出与场景对应的问题：“如果这份材料今天就要交给目标接收方，这句话应该出现在这个位置吗？”投稿材料改用：“如果今天投稿，这句话应该出现在这一章节、这一段、这个位置吗？”

合格句须同时满足：

- 服务正式用途、核心主张或必要信息；
- 位于承担相应功能的文种、章节和段落；
- 与前后句构成清楚的信息或论证关系；
- 面向接收方表达，脱离协作过程仍可自然理解；
- 没有编辑语言、内部状态、过程说明、模型痕迹和自我保护式保留；
- 删除后会实质削弱内容、论证、责任、合规或使用效果。

不合格句执行重写、移动、内部隔离或删除。仅删去风险词而保留内部句法，不得视为完成清理。

### 4.5 立场型正式内容

用户要求论述、倡议、说服或支持某项判断时：

- 将用户指定主张作为论证终点；
- 选择最有力且准确的事实、逻辑、机制、价值依据和现实影响；
- 组织从问题、理由、支持、解释到结论或行动的连续链条；
- 减少无目的的中立综述、反方意见堆叠和立场稀释；
- 受众确有需要时处理反方意见，并给出直接回应；
- 来源稿中已经存在的泛化保留、无来源反方意见和自我保护式声明默认删除，禁止换词保留；
- 目标文种明文要求局限、风险或披露时，以正式、具体、简洁的方式放在规定位置；
- 不虚构事实、数据、引文、来源或确定性。

## 5. 七层门禁

1. **意图层**：识别用户是否要求最终可用结果。
2. **目标层**：确认用户指定主张、接收方和预期行动。
3. **句级层**：逐句判断用途、位置、表达、方向和必要性。
4. **文种层**：判断内容是否属于目标文种及当前位置。
5. **文件系统层**：检查名称、版本、临时文件、目录和允许清单。
6. **容器层**：检查批注、修订、备注、隐藏区域、附件和属性。
7. **语义层**：检查过程泄漏、编辑语言、内部状态和无正式用途内容。
8. **发布层**：核对最终目录、压缩包、链接和实际文件。

脚本只覆盖确定性结构与关键词候选。语义门禁必须由执行者完成。

## 6. 处理原则

- 从交付目录排除内部文件，保留内部原件。
- 在副本中进行获准的最小修改。
- 将内部意见提炼为正式事实、证据、立场或行动。
- 对污染句执行重新写作，避免局部删词。
- 围绕用户指定主张编排理由、事实、解释和行动，保持全文论证方向稳定。
- 将内部准确性核查留在工作区，禁止把核查顾虑转写为无正式用途的正文保留。
- 将正式回应放入回应文件，将内部理由放入内部记录。
- 发现无法确认的发布风险时停止发布并请求用户决定。
- 用户明确要求某个内部性质文件作为正式附件时，记录例外并按用户要求交付。

## 7. 完成标准

通过状态要求：

- `block` 为零；
- `review` 均有语境结论；
- 例外均有用户授权；
- 交付目录与允许清单一致；
- 核查报告位于交付目录之外；
- 成品脱离当前对话后能够独立使用；
- 每句话和每个对象均通过场景化成稿适格判断；
- 立场型交付持续服务用户指定主张，没有被习惯性保留或无目的平衡段落稀释；
- 外部读者不会看到模型、用户、修改过程或内部工作状态；
- 清理未改变未经授权的正式内容。
