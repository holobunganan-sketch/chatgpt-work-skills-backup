# 人在回路式正式修订

## 执行核心约束

- 将源文件视为只读基线；复制后再工作，禁止覆盖原件。
- 逐字保存每条反馈原文；将翻译、概括、解释与原文分栏存放。
- 同时使用原文锚点和上下文语义定位；将页码、行号、条款号等坐标仅作线索。
- 先分类、识别关联和提出建议，再请求责任决策者作出明确决定。
- 将咨询意见标记为建议性输入；仅由责任决策者批准、拒绝、延后或附条件批准。
- 在批准范围内实施修改；禁止把沉默、缺少批注或咨询方意见推定为批准。
- 使正式回应逐项对应实际改动；禁止声称尚未完成的修改。
- 保持独立运行；缺少交换台账时自行建立最小台账，存在兼容台账时按需复用。

## 读取配套资源

1. 每次使用时完整阅读 [SPEC.md](references/SPEC.md)，按其中的不变量和阶段门执行。
2. 需要与其他 Skill、代理或系统交换状态时，完整阅读 [INTERCHANGE_CONTRACT.md](references/INTERCHANGE_CONTRACT.md)。
3. 处理学术论文、审稿意见或审稿回复时，额外完整阅读 [ACADEMIC_PROFILE.md](references/ACADEMIC_PROFILE.md)。
4. 开发、回归测试或评估泛化能力时，完整阅读 [EVALUATION_CASES.md](references/EVALUATION_CASES.md)。

## 按阶段推进

### 1. 建立边界并锁定源文件

1. 识别责任决策者、反馈来源、咨询方、实施者、正式接收方和任务范围。
2. 区分原始来源、工作副本、内部记录、正式交付物和派生文件。
3. 记录源文件清单、版本、路径或稳定标识、内容摘要值和锁定时间。
4. 在工作副本中开展后续操作；检测到源文件变动时暂停并重新建立基线。

### 2. 保真采集反馈

1. 按来源顺序逐条采集完整原文，保留原编号、层级、限定条件和上下文。
2. 为每条反馈分配稳定且唯一的条目编号。
3. 分开记录原文、翻译、核心问题、解释和建议；禁止用概括替换原文。
4. 计算原文摘要值；后续导出前复核原文未被改写、截断或重排。

### 3. 完成语义定位与分类分流

1. 检索反馈引用的原句、术语、数值、对象和近义表达。
2. 阅读命中位置前后文，判断反馈实际指向的内容和传播范围。
3. 记录语义锚点、坐标准确性、定位依据和未决歧义。
4. 将条目分类为直接内容修改、证据检索、数据或计算重做、图形或结构调整、仅正式回应、需要决策、受阻或其他。
5. 标注所需权限、信息、工具、成本和风险；禁止在分类阶段提前实施修改。

### 4. 建立关联图并形成决策材料

1. 标记重复、重叠、包含、依赖、冲突、前置和传导关系。
2. 识别一项决定对其他条目、文件、术语、数值、编号和正式回应的影响。
3. 为每条反馈给出可执行建议、备选方案、影响范围、风险和推荐理由。
4. 形成可批注台账；保留每条反馈的独立位置，同时提出可合并实施的工作包。
5. 对“同前”“沿用前述意见”等指代追溯到具体条目和具体原则。

### 5. 执行责任决策门

1. 向责任决策者提交完整分析和明确选项。
2. 记录批准、拒绝、延后或附条件批准的条目、范围、条件、人员和时间。
3. 将用户针对具体修改的明确执行指令记录为该范围的批准；将探索性问题、意见征询和模糊表态保持为待决。
4. 检查冲突、依赖和条件均已解决后再允许实施。
5. 对未获批准的条目保持未修改状态；继续开展不改变正式内容的只读分析。

### 6. 仅在批准范围内实施

1. 从已批准且依赖满足的条目开始实施。
2. 记录每项实际改动的文件、位置、改前内容、改后内容和变更编号。
3. 发现需要扩展批准范围时暂停该扩展，补充影响分析并重新请求决定。
4. 协调关联条目和下游文件；保持术语、数值、编号、引用和结论一致。
5. 保留拒绝、延后和仅回应条目的原状态，禁止借联动修改绕过决定门。

### 7. 同步正式回应

1. 针对每条需要回应的反馈保留完整原文和独立回应位置。
2. 依据责任决策和已经完成的改动撰写回应，说明接受程度、实际行动、理由和可核查位置。
3. 对拒绝、部分接受或无须修改的条目给出清楚理由；禁止虚构修改位置。
4. 使用变更编号连接回应声明与实际改动。
5. 修改正文、附件或其他交付物后同步更新受影响的回应。

### 8. 验证并释放

1. 逐条核对“反馈原文—语义定位—决定—实际改动—正式回应—交付证据”。
2. 使用 `python scripts/validate_revision_ledger.py <台账.json> --decision-gate <决定门.json> --stage release --verify-files` 执行确定性检查；无法访问源文件时省略 `--verify-files` 并人工核对锁定证据。
3. 对脚本无法判断的语义一致性、写作质量和回应充分性进行人工复核。
4. 确认所有待决条目均已处理为批准、拒绝或延后，并清楚标识其交付状态。
5. 仅在核查通过后释放正式交付物；将内部台账和决定记录保存在正式交付范围之外。

## 使用模板与协议

- 从 [revision-ledger.template.json](assets/revision-ledger.template.json) 复制返修台账，禁止直接覆盖模板。
- 从 [decision-gate.template.json](assets/decision-gate.template.json) 复制决定门记录。
- 无需跨系统交换时仍可使用普通表格或文档，但须保留规范要求的等价字段和证据链。
- 接收外部台账时先验证版本和字段；无法兼容时只导入可验证事实，并记录转换过程。

## 处理阻塞与异常

- 无法确定责任决策者时停止内容修改，并请求明确授权主体。
- 无法保真取得反馈原文时标记来源缺口，禁止凭记忆补写。
- 无法定位时记录候选位置和歧义，请求决定或补充材料。
- 咨询意见冲突时并列呈现理由和影响，等待责任决策者裁定。
- 发现源文件或批准范围发生变化时关闭旧决定门，重新分析受影响条目。
- 发现回应与实际修改不一致时阻止释放，先修正事实链。
