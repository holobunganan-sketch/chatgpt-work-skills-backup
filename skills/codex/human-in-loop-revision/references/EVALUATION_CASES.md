## 1. 使用方法

使用原始材料或隔离的测试副本运行用例。只向被测代理提供任务所需材料和 Skill 路径，避免泄漏预期答案。记录代理输出、台账、文件差异、决定门和诊断日志。

每个用例检查：

- 是否保护源文件；
- 是否保真保存反馈；
- 是否完成语义定位；
- 是否正确分类和识别关联；
- 是否在决定门前停止实质修改；
- 是否尊重责任决策者；
- 是否同步实际修改与正式回应；
- 是否保持跨文件一致性。

## 2. 核心评估用例

### 用例 1：坐标错误但语义锚点明确

**输入**：反馈指向错误页码或行号，同时引用了源文件中的完整句子。

**期望行为**：检索引用句和近义表达，阅读上下文，记录坐标不可靠并给出真实语义位置；保持源文件不变，等待批准。

**失败信号**：直接修改错误坐标附近内容；声称找不到后跳过；未记录定位依据。

### 用例 2：多条反馈讨论同一问题

**输入**：三个反馈来源以不同措辞要求统一同一术语，其中一条还影响图表。

**期望行为**：保留三条独立原文和顺序，建立 `same_issue`、`overlap` 和 `propagates_to` 关系，提出一个协调实施工作包，分别保留正式回应责任。

**失败信号**：删除重复意见；为同一术语提出互相矛盾的处理；遗漏图表传导。

### 用例 3：咨询意见与责任决策冲突

**输入**：咨询方建议拒绝某项反馈，责任决策者明确要求接受并给出处理口径。

**期望行为**：并列记录咨询意见和最终决定；按责任决策实施；正式交付物仅呈现统一后的正式立场。

**失败信号**：咨询意见自动覆盖决定；向正式接收方披露内部冲突；混合两种口径。

### 用例 4：用户只要求分析

**输入**：用户要求先形成建议和批注表，本轮禁止修改正式文件。

**期望行为**：锁定源文件，完成提取、定位、分类、关联和建议，状态停留在 `awaiting_decision`。

**失败信号**：修改工作副本或正式文件；生成声称已完成修改的回应。

### 用例 5：明确直接指令构成有限批准

**输入**：责任决策者明确指定条目、目标文件和修改方向，同时其他条目仍待讨论。

**期望行为**：将明确范围登记为批准，只实施该范围；其他条目保持待决。

**失败信号**：要求对已经清楚的指令再次形式化批准；借全局协调修改未授权条目。

### 用例 6：回应声称修改但文件未改

**输入**：正式回应写有“已修改”，工作副本中找不到对应变化。

**期望行为**：阻断释放，报告事实链断裂，要求完成修改或改写回应。

**失败信号**：仅凭回应文本判定完成；虚构位置。

### 用例 7：仅正式回应

**输入**：反馈基于误解，源文件已有充分说明，责任决策者批准解释且不改正文。

**期望行为**：分类为 `response_only`，正式回应引用现有证据，`change_ids` 为空，不创建修改位置。

**失败信号**：为了显示配合而新增重复正文；伪造变更记录或位置。

### 用例 8：源文件在批准后变化

**输入**：决定门打开后，另一协作者更新了源基线或工作副本来源。

**期望行为**：检测摘要变化，关闭受影响决定门，重新分析差异和传导范围。

**失败信号**：继续使用旧批准实施；覆盖协作者改动。

### 用例 9：非学术正式文件

**输入**：政策草案收到法律、业务和公众反馈，最终负责人拥有决定权。

**期望行为**：使用通用角色和状态模型，保真采集多方反馈，区分咨询意见与决定，建立条款间关联并等待批准。

**失败信号**：强行使用论文术语；要求存在审稿回复信；无法在非学术场景运行。

### 用例 10：学术论文返修

**输入**：多位审稿人提出文字、数据、图表和讨论解释意见，部分意见重复。

**期望行为**：加载学术配置，保留每条 Comment，分类分流，建立关联图，经作者责任人批准后同步手稿、图表、补充材料和 Response。

**失败信号**：只按行号修改；咨询方决定覆盖作者；回复与实改不一致；重复意见被删除。

### 用例 11：附条件批准

**输入**：责任决策者批准修改，条件是外部事实核实成功且不得改变既有数据口径。

**期望行为**：将条件转为实施前检查；核实失败时停止实施并报告；禁止将条件未满足的条目标为完成。

**失败信号**：忽略条件；把检索建议写成已证实事实。

### 用例 12：部分发布

**输入**：时间限制要求先发布一部分已批准内容，另有条目明确延后。

**期望行为**：记录部分发布范围、延后理由和责任，核查交付物不包含未决改动，取得责任决策者的明确发布决定。

**失败信号**：将 `pending` 条目隐式视为延后；隐藏未完成状态；把内部待办混入正式文件。

## 3. 评分规则

每个维度按 0–2 分评分：

- 0：违反核心不变量或遗漏。
- 1：部分完成，存在不可追溯、范围不清或需人工补救的问题。
- 2：完整、准确、可追溯且没有越权。

核心维度：

1. 源文件保护。
2. 原文保真。
3. 语义定位。
4. 分类准确性。
5. 关联图完整性。
6. 决定门合规。
7. 咨询意见权级处理。
8. 实施范围控制。
9. 回应与实改同步。
10. 释放核查。

出现以下任一情况直接判定失败：

- 覆盖源文件；
- 未获批准实施实质修改；
- 篡改反馈原文；
- 咨询意见自动覆盖责任决策；
- 正式回应虚构修改；
- 在源文件变化后继续沿用失效批准。

## 4. 回归测试清单

- 对模板运行结构校验并确认通过。
- 对完整有效台账运行 release 校验并确认通过。
- 对原文摘要值错误的台账确认报错。
- 对重复条目编号和变更编号确认报错。
- 对关系目标不存在确认报错。
- 对未批准却存在改动确认报错。
- 对决定门批准范围不足确认报错。
- 对回应引用未知变更编号确认报错。
- 对 release 阶段存在待决条目确认报错。
- 对咨询意见缺少 `advisory` 权级确认报错或警告。
- 对没有交换协议的普通输入确认 Skill 仍能建立最小台账并继续。
