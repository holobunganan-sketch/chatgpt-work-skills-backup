## 1. 目标与适用边界

本规范用于管理一个修改在多个内容载体、版本和派生文件之间的传导。目标是保持事实、语义、数值、结构、引用和版本一致，同时保护授权边界、原有内容和可追溯性。

将本规范用于以下任务：

- 多个文档、图表、附件或演示文件共享同一事实；
- 同一内容存在清洁版、标记版、语言版本或渠道版本；
- 一项反馈可能影响多个章节或交付物；
- 修改声明需要与实际文件证据核对；
- 用户要求全局协调、同步更新、版本一致或发布前核查。

仅处理用户置于任务范围内的对象。把范围外关联项记录为潜在影响，不执行写入。

## 2. 规范术语

### 2.1 产物

任何需要登记、比较、修改或发布的内容载体，包括文档、表格、图像、数据文件、演示文稿、代码、配置、回应材料和压缩包。

### 2.2 角色

- **权威源（authoritative）**：某项内容或事实的最终裁决来源。
- **工作文件（working）**：修改过程中使用、尚未批准发布的文件。
- **派生物（derived）**：由一个或多个上游产物生成或同步的文件。
- **正式交付物（deliverable）**：计划提供给外部接收者的文件。
- **内部产物（internal）**：用于决策、追踪、核查或记录的文件。

同一产物可以同时属于派生物和正式交付物。使用 `role` 表示主角色，使用 `tags` 表示附加身份。

### 2.3 规范项

需要跨产物保持一致的最小事实单元。规范项至少包含：

- 稳定键；
- 维度；
- 规范值；
- 语义或口径；
- 权威产物；
- 定位证据；
- 已知出现位置。

### 2.4 变更影响图

以产物为节点、以派生或同步关系为有向边的图。边必须声明适用维度和传导模式。影响计划沿图计算直接与间接目标。

### 2.5 实际改动记录

对已经写入文件的变化进行事实性记录。每条记录包含产物、定位、改前内容、改后内容、执行状态和核验证据。计划动作不得标记为实际完成。

## 3. 权限与认识论原则

### 3.1 最小授权

- 把用户明确提供的写入范围设为最大写入边界。
- 允许在任务范围内执行必要的只读定位和一致性检查。
- 把超出写入边界的受影响产物标记为 `requires_authorization`。
- 不因技术上可访问而推定用户已经授权修改。
- 不因一项修改“更完整”而扩大研究、业务、法律或设计结论。

### 3.2 来源优先

- 先确认文件身份、版本和权威级别，再采信内容。
- 在两个候选权威源冲突时暂停相关传导。
- 不用派生物反向覆盖权威源，除非用户明确重新指定权威关系。
- 不把回应、报告或摘要中的陈述自动视为基础事实。

### 3.3 证据优先

- 用真实文件位置证明改动已经完成。
- 将“拟修改”“已建议”“已回复”与“已写入并核验”分开记录。
- 对无法程序化验证的语义一致性执行人工或模型复核，并记录方法。
- 避免根据文件名、日期或记忆推断版本身份；结合内容指纹、元数据和来源关系确认。

### 3.4 最小充分修改

- 只改动实现授权目标所必需的内容。
- 保留无关文字、格式、公式、域代码、链接、批注策略和用户已有改动。
- 优先修改权威源并重新生成派生物。
- 在无法可靠重新生成时，对每个派生物执行受控同步并记录差异。

## 4. 强制不变量

### 4.1 唯一权威来源

- 每个规范项必须只有一个 `source_artifact_id`。
- 权威来源必须包含可核查定位。
- 同一事实存在多种合法口径时，为每种口径建立不同规范项，并明确适用上下文。
- 同一键出现冲突值时，阻断相关发布。

### 4.2 有向派生关系

- `derived_from` 图必须无循环。
- 每个派生物必须指向已登记的上游产物。
- 每条传播边必须声明适用维度。
- 传播边不得自动赋予写权限。

### 4.3 同源版本

- 清洁版与标记版必须由同一规范化内容源生成。
- 两个版本的允许差异必须在发布集合中显式声明。
- 默认只允许高亮、修订标记、批注可见性、展示性元数据等表现层差异。
- 正文、表格单元格、公式、图片数据、引用目标和编号差异均视为内容漂移，除非发布集合明确授权。

### 4.4 事实闭环

每项修改必须形成以下闭环：

`请求或事实变化 → 授权决定 → 影响计划 → 实际改动 → 核验证据 → 发布状态`

任何环节缺失时，不得声明整项修改完成。

### 4.5 全局协调

- 对术语、数字、编号、引用和版本执行专门检查。
- 对标题、正文、图表、附件、目录、交叉引用、回应和发布说明执行关系检查。
- 允许某一位置基于上下文保留不同措辞；记录语义等价理由。
- 禁止仅凭字符串命中批量替换语义不明的内容。

### 4.6 实际状态真实

- 仅在目标文件已经修改且完成核验时使用 `verified`。
- 使用 `not_applicable` 时记录无需修改的理由。
- 使用 `requires_authorization` 时记录所需权限。
- 使用 `blocked` 时记录阻断事实和解除条件。
- 不以百分比、模糊措辞或笼统结论掩盖未关闭项目。

## 5. 标准工作流

### 阶段 A：发现与冻结

1. 列出任务涉及的全部产物。
2. 记录路径、格式、角色、版本、校验摘要或其他身份信息。
3. 标识原始文件和用户已有改动。
4. 冻结权威关系；在未澄清前保持只读。

### 阶段 B：建模

1. 创建产物登记表。
2. 建立 `derived_from` 和 `propagation_rules`。
3. 识别共享规范项及其出现位置。
4. 建立发布集合和允许差异。
5. 运行登记表校验。

### 阶段 C：影响分析

1. 将修改请求拆分为最小规范项更新。
2. 标记维度、改前值、改后值和决策依据。
3. 生成直接目标和传递目标。
4. 依据授权范围分流为可执行、需授权和只读核查。
5. 由用户或负责方确认存在实质判断的计划。

### 阶段 D：执行

1. 按拓扑顺序修改权威源和派生物。
2. 对每个位置执行语义核对。
3. 同步结构、引用、目录、图表和版本信息。
4. 逐条写入实际改动记录。
5. 在工具可能破坏格式、链接、域或公式时先建立可恢复副本。

### 阶段 E：验证

1. 检查所有规范项出现位置。
2. 比较同源版本的规范化内容。
3. 核对交叉引用、编号、引用目标和文件间链接。
4. 核对修改声明与实际证据。
5. 重新运行影响计划，确认无未关闭的授权内任务。

### 阶段 F：发布

1. 使用允许清单组装发布集合。
2. 排除内部记录、缓存、锁文件和中间产物。
3. 记录交付物版本和指纹。
4. 将未授权影响、已知限制和待决事项保留在内部交接信息中。

## 6. 状态模型

### 6.1 变更状态

- `proposed`：已经提出，尚未批准。
- `authorized`：已获准执行。
- `in_progress`：正在实施。
- `implemented`：已经写入，尚未完成验证。
- `verified`：已经写入并完成验证。
- `not_applicable`：经核对无需修改。
- `requires_authorization`：影响成立，缺少写权限。
- `blocked`：缺少事实、来源或工具条件。
- `rejected`：决策方明确不采纳。

### 6.2 产物状态

- `source_locked`：来源和版本已确认。
- `working`：处于编辑中。
- `sync_pending`：存在待同步变化。
- `verified`：已通过当前轮一致性核验。
- `release_ready`：已通过发布门。

状态变化必须有证据和时间记录。禁止从 `proposed` 直接跳到 `verified`。

## 7. 冲突与失败处理

### 7.1 权威源冲突

列出冲突值、各自来源、版本和影响范围。暂停相关规范项的写入。请求具有决定权的人员指定规范值或权威源。

### 7.2 版本身份不明

比较文件内容、修改时间、内嵌元数据、引用关系和用户说明。无法确认时保留候选文件，禁止覆盖。

### 7.3 影响范围超过授权

继续完成授权内修改与只读核查。将范围外对象标记为 `requires_authorization`，提供具体路径、影响维度和预期动作。不要静默忽略，也不要擅自修改。

### 7.4 无法自动验证

记录验证限制，执行针对性人工复核。把验证方法、抽样范围和剩余风险写入内部审计记录。不得把“脚本未报错”等同于语义一致。

### 7.5 派生物无法重建

确认是否允许直接同步。若允许，逐项修改并记录来源；若不允许，保留影响计划并标记阻断。不得用近似重建产物覆盖原文件。

## 8. 输出与发布规则

### 8.1 内部输出

- 产物登记表；
- 规范项清单；
- 变更记录；
- 影响计划；
- 核验证据；
- 未授权或阻断事项。

默认把这些内容保留在正式交付集合之外。

### 8.2 正式输出

正式输出仅包含用户批准的交付物。每个文件应具备稳定名称、版本标识和可核对内容。发布集合不得混入内部决策记录、临时文件或旧版本。

### 8.3 完成声明

只有在以下条件全部满足时声明“全局一致性修改完成”：

- 所有授权内影响项均为 `verified` 或 `not_applicable`；
- 所有 `requires_authorization` 和 `blocked` 项均已明确报告；
- 同源版本通过内容一致性比较；
- 正式声明均有实际证据；
- 发布集合通过允许清单检查。
