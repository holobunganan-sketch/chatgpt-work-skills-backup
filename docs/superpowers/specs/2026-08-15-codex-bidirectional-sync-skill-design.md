# Codex Skills 与插件双向同步 Skill 设计

日期：2026-08-15  
设计基线：`097f4d1cb1752c16c949e4a122ec18b393a59ed5`  
目标仓库：`holobunganan-sketch/chatgpt-work-skills-backup`  
Skill 名称：`syncing-codex-skills-and-plugins`

## 目标

创建一个可由 Codex 自动发现的个人 skill。用户每次启动它时先选择同步方向，系统完成扫描并展示一份差异汇总，用户统一确认一次，后续同步、去重、校验、Git 提交或本地安装全部自动执行。

支持两个方向：

- 云端到本地：从私有 GitHub 仓库安装或更新个人 skills、共享支持文件和个人插件。
- 本地到云端：从当前计算机收集白名单内容，构建去重备份并推送到私有 GitHub 仓库。

完成后的设计不变量：

- 内容完全相同的目标自动跳过。
- 同名但内容不同的目标进入冲突汇总，未经本次明确确认不得覆盖。
- 每次写入前都展示汇总并等待一次确认。
- 确认后不再提出过程性问题；身份验证、源数据变化或校验失败属于停止条件。
- 系统 skills、官方插件、凭据、配置、日志、会话和运行缓存不进入备份。
- 插件保持自包含，恢复后的 Codex 与 Agent 发现路径保持有效。
- 同步 skill 自身进入仓库，并在新计算机上随云端安装一同恢复。

## 与已有去重设计的关系

本设计扩展 `2026-08-14-skill-deduplication-design.md`：

- 保留该设计的权威源码规则、`restore-map.json`、物理目录去重和恢复计数逻辑。
- 将原安装脚本的覆盖行为改为“计划、汇总确认、应用”的两阶段行为。
- 新增本地到云端方向、同步报告和远端并行更新保护。
- 新 skill 加入后，目标物理 skill 目录为 49 个；恢复后 Codex 用户级 skills 为 37 个、Agent skills 为 26 个、插件内嵌 skills 为 12 个。

## 方案比较

### 方案 A：Skill 协调器与确定性 PowerShell 引擎（采用）

`SKILL.md` 负责触发、方向选择、展示计划和获取确认。PowerShell 脚本负责扫描、哈希、去重、复制、备份、Git 操作和报告。脚本提供分离的计划与应用阶段，使用户确认对应一个冻结的计划。

优点：行为可重复、可测试、适合 Windows Codex 环境；确认边界清楚；首次克隆和后续同步使用同一实现。代价：需要维护脚本和测试夹具。

### 方案 B：仅使用 SKILL.md 指挥 Codex

由 Codex 每次临时组合文件检查和 Git 操作。适应性较强，执行细节与报告结构容易随会话变化，因此不采用。

### 方案 C：Git 钩子或定时镜像

在文件变化时自动推送或拉取。该方式缺少每次汇总确认，容易把暂存文件或异常版本同步出去，因此不采用。

## 组件与职责

### Skill 目录

```text
skills/codex/syncing-codex-skills-and-plugins/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   └── sync-codex-assets.ps1
└── references/
    └── SYNC_CONTRACT.md
```

- `SKILL.md`：保持简洁，定义触发条件、交互顺序、停止条件和脚本调用方式。
- `agents/openai.yaml`：提供显示名称、简短说明和默认启动提示。
- `sync-codex-assets.ps1`：唯一同步引擎，提供计划、应用和验证入口。
- `SYNC_CONTRACT.md`：记录白名单、排除项、计划格式、冲突规则和报告字段。

Skill 目录不包含 README、安装指南或变更日志。

### 仓库级入口

- `install.ps1` 调用同步引擎的云端到本地能力，保留首次克隆后的直接安装入口。
- `verify.ps1` 校验物理目录、恢复映射、来源哈希、逻辑目标计数、插件清单和包哈希。
- `restore-map.json` 继续作为省略的重复目录与恢复目标之间的权威映射。
- `inventory.json` 区分物理源码、恢复目标、排除项和同步 skill 自身。
- `README.md` 与 `BACKUP_SCOPE.md` 说明启动方式、白名单和冲突策略。

## 交互协议

### 第一次选择：同步方向

Skill 启动后只提供：

1. 云端到本地。
2. 本地到云端。

选择方向后，Codex 调用同步引擎生成只读计划。计划阶段可以克隆、抓取和读取临时工作区，不得修改正式目标或推送远端。

### 第二次选择：汇总确认

每次运行都展示以下分类及数量：

- `add`：仅来源端存在，计划新增。
- `identical`：名称和内容哈希一致，自动跳过。
- `conflict`：名称相同且内容不同。
- `extra`：仅目标端存在，默认保留。
- `deduplicated-source`：物理副本将由恢复映射替代。
- `blocked`：身份、敏感信息、清单或并行更新问题。

确认选项：

1. 保留目标端冲突版本，只新增缺失项目。
2. 使用来源端版本替换全部冲突项目；本地替换前创建备份，云端替换由 Git 历史保留旧版本。
3. 取消本次同步。

确认适用于当前计划哈希。确认后任一来源文件、目标文件或远端提交发生变化，应用阶段必须拒绝旧计划并重新扫描、汇总和确认。

## 同步白名单

### Codex 用户级内容

- `~/.codex/skills` 下含 `SKILL.md` 的直接子目录。
- `~/.codex/skills/.shared` 下被用户级 skill 引用的共享支持目录。
- 排除 `~/.codex/skills/.system`。

### Agent 用户级内容

- `~/.agents/skills` 下含 `SKILL.md` 的直接子目录。

### 个人插件

- `~/plugins/medical-manuscript-workflow`。
- `~/.agents/plugins/marketplace.json` 中名称为 `medical-manuscript-workflow` 的单个条目。

### 固定排除

- `~/.codex/plugins/cache`。
- Codex 系统 skills、官方插件与远程插件数据。
- `config.toml`、认证令牌、Git 凭据、浏览器状态、日志、会话和安装标识。
- `__pycache__`、`*.pyc`、临时文件和编辑器缓存。
- 不在白名单中的用户目录内容。

## 内容哈希与目标身份

同步单位为一个 skill 目录、`.shared` 支持目录、插件目录或 marketplace 条目。

目录树哈希算法：

1. 应用固定排除规则。
2. 将相对路径统一为 `/`，按序数顺序排序。
3. 计算每个文件的 SHA-256。
4. 对“规范化路径、文件哈希”序列再次计算 SHA-256。
5. 检测仅大小写不同的路径；发现后将计划标记为 `blocked`。

目标身份由目标根目录与名称共同确定。因此 `.codex` 与 `.agents` 下的同名 skill 可以作为两个逻辑目标存在。

## 去重规则

1. 插件必须保持自包含。插件内嵌 skill 与 standalone 副本完全相同时，以插件目录为权威源码。
2. Codex 与 Agent 的同名 standalone skill 内容完全相同，且插件未提供该内容时，以 Codex 目录为权威源码。
3. 同名目录的树哈希不同，保留各自源码并列为独立内容分支。
4. 每个被省略的物理副本写入 `restore-map.json`，记录来源、目标根目录、skill 名称和来源树哈希。
5. 逻辑项目从来源端消失时，不自动删除目标端项目，统一列为 `extra`。
6. 物理重复副本的删除属于去重计划，只有在恢复映射通过验证且用户批准本次汇总后执行。

## 云端到本地流程

1. 检查 `git`、GitHub CLI 和 GitHub 登录状态。
2. 将私有仓库 `main` 分支克隆或更新到 `~/.codex/sync-workspaces/chatgpt-work-skills-backup`。
3. 在临时检出目录验证 `SHA256SUMS.txt`、插件清单、marketplace、库存和恢复映射。
4. 从物理源码和恢复映射生成完整逻辑安装集合。
5. 扫描本地白名单目标并生成计划与计划哈希。
6. 展示汇总并等待一次确认。
7. 按确认策略安装缺失项目、跳过相同项目、处理或保留冲突。
8. 合并个人插件 marketplace 条目，不改动其他插件条目。
9. 验证安装结果并写出运行报告。

本地替换使用 `~/.codex/sync-backups/<run-id>/` 保存受影响项目。应用失败时只回滚本次已写入的目标。

## 本地到云端流程

1. 检查 `git`、GitHub CLI、GitHub 登录状态和私有仓库访问权限。
2. 扫描白名单目录并建立来源快照；源文件在扫描过程中变化时停止。
3. 运行凭据特征、绝对路径、缓存和文件大小检查。
4. 在临时目录构建规范化包，执行物理目录去重并生成恢复映射。
5. 重新生成库存和 `SHA256SUMS.txt`，运行仓库验证。
6. 获取远端 `main` 的最新提交，比较来源包、远端包和当前计划。
7. 展示新增、相同、冲突、额外项目和物理去重汇总，等待一次确认。
8. 按确认策略更新临时工作区，再次运行验证。
9. 创建 Git 提交并推送 `main`。
10. 通过 GitHub API 核对远端提交、私有可见性、插件清单和文件树。
11. 写出运行报告。

远端提交在确认后发生变化时停止推送。推送失败时保留本地提交和报告，不声明同步成功。

## 计划与报告

计划文件至少包含：

- `schemaVersion`、`runId`、方向、生成时间和计划哈希。
- 来源提交、目标提交和仓库地址。
- 白名单与排除规则版本。
- 每个同步单位的身份、来源、目标、树哈希、分类和拟执行动作。
- 阻断项、警告和确认策略。

报告保存到 `~/.codex/sync-reports/<run-id>.json`，同时输出简短中文摘要。报告记录新增、跳过、冲突、备份、提交、推送、验证和失败证据，不记录令牌或凭据内容。

## 错误处理与回滚

- GitHub 未登录或无仓库权限：停止并说明登录要求，不修改目标。
- 包哈希、插件清单或恢复映射无效：停止并保存验证证据。
- 发现敏感信息或不允许的路径：阻断本地到云端计划。
- 本地写入失败：使用本次备份恢复已修改项目，保留未触及项目。
- 计划过期：拒绝应用并要求重新生成汇总。
- 远端并行更新：停止推送并重新进入计划阶段。
- 网络或推送失败：保留本地提交和报告，后续运行重新比较远端。
- 用户取消：删除临时计划和临时工作区中的未提交构建产物，保留报告摘要。

## 测试策略

### Skill TDD

在创建 `SKILL.md` 前，使用未加载该 skill 的新上下文运行基线场景并记录失败行为：

1. 本地已有相同与冲突 skill，要求云端到本地同步。
2. 本地包含凭据特征和运行缓存，要求本地到云端同步。
3. 用户催促跳过汇总确认并直接覆盖。
4. 用户确认后远端提交发生变化。

完成 skill 后，用相同场景复测，要求 Codex始终先生成计划、展示一次汇总、等待确认并遵守停止条件。

### 引擎测试

- 哈希稳定性、排除规则和大小写冲突。
- 空目标安装、部分已有、全部相同和同名差异。
- 三种汇总确认结果。
- 恢复映射生成、来源哈希漂移和目标唯一性。
- marketplace 合并并保留无关条目。
- 本地失败回滚和过期计划拒绝。
- 使用临时用户根目录完成云端到本地集成测试。
- 使用临时 Git 远端完成本地到云端提交与并行更新测试。
- 连续执行相同方向两次，第二次没有新增写入。

### 发布验证

- 使用 `quick_validate.py` 验证 skill 结构和 frontmatter。
- 验证 `agents/openai.yaml` 与 `SKILL.md` 一致。
- 验证仓库物理 skill 目录为 49，恢复后的逻辑计数为 Codex 37、Agent 26、插件 12。
- 验证完全相同的跨根目录物理副本组为 0。
- 验证凭据特征、旧计算机绝对路径、运行缓存和 GitHub 文件大小限制。
- 推送后核对远端提交、私有可见性、skill 文件、插件文件和包哈希。

## 验收标准

- Skill 可以通过自然语言请求或技能列表触发。
- 每次运行只需要选择方向并对差异汇总统一确认一次。
- 用户确认后，同步过程无需追加选择；停止条件会给出清晰报告。
- 完全相同项目不产生复制、备份或 Git 内容变更。
- 冲突项目未经本次确认不会被覆盖。
- 本地到云端不会上传固定排除项或敏感信息。
- 云端到本地不会改动无关 skills、插件或 marketplace 条目。
- 重复运行具备幂等性。
- 新 skill 自身已安装到当前 Codex、已纳入备份并已推送私有仓库。

## 发布顺序

1. 完成 Skill TDD 基线场景。
2. 实现并验证同步引擎。
3. 创建最小 `SKILL.md`、同步契约和 UI 元数据。
4. 更新根安装器、验证器、恢复映射、库存和说明文件。
5. 执行临时环境双向同步测试和重复运行测试。
6. 安装新 skill 到当前 `~/.codex/skills`。
7. 提交全部实施变更并推送私有仓库。
8. 通过 GitHub API 完成远端核验。
